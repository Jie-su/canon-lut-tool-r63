# 为什么 R7 方案不能直接用于 R6 Mark III

本文整理一次 R6 Mark III／固件 1.1.2 的历史开发结果。原始相机数据、私人原片和安装备份不随公开仓库提供，因此下面的硬件结果属于本项目报告的限定实测，公开源码测试不能独立代替它们。

## 核心结论

R7 的 CUBE→PF3 思路可以复用，但不能直接复用机型上下文、安装载荷和验证假设。

本次 R6 III 的官方注册输入是 **431,616 字节 full33**，独立设备读回却是 **83,076 字节 packed17 表示**。早期尝试因为读回长度与 R7 相同，强制走 R7/type9 生成写入数据，恒等 LUT 也出现了伪色。成功路线保留真实 R6 III 型号、描述符和 type10，在正常原生 full33 输出中替换两张色表，再以真实新读取、机内 JPEG 和一次重启验收。

## 两条机型路线

| 项目 | 原 R7 研究路线 | 本次 R6 III 路线 |
| --- | --- | --- |
| 型号 | `0x80000464` | `0x80000518` |
| 编译分类 | type9／modern17 | type10／full33 |
| 写入载荷 | 83,076 字节 | 431,616 字节 |
| 主体 | 372 字节头＋四张 packed 17³ 表＋4,096 字节辅助区 | 372 字节头＋两张 planar RGB 33³ 表 |
| R6 III 的独立读回 | 不适用 | 83,076 字节，和写入输入不同 |

PF3 源文件本身又是另一种对象。两张 PF3 源表位于 `0x40001070`、`0x40001071`，每张为 33³、RGB、12-bit，连几何头共 215,628 字节。不能根据 PF3 文件长或 getter 长度推断 setter 的数据合同。

## 早期失败与假阳性

早期移植修改了本地接口的机型分类，使其选择 R7/type9，而 profile 仍保存 R6 III 型号。这种混合上下文没有证明等价于真实 R6 III 路线。

恒等候选的 setter 返回 0，同会话 getter 与输入完全一致，但实际取景伪色。固定版本 SDK 的 setter 会更新属性缓存，因此紧随其后的 getter 可能回显原输入。另建会话读取后，83,076 字节中有 81,967 字节不同，372 字节头保持一致。

这些事实否定了该候选和当时的验证标准，但没有完整定位机身内部每一级导致伪色的编码或 DSP 机制。不能据此断言“固件锁死”“双重加密”或“R6 III 无法使用照片 LUT”。

## 成功时修改了什么

### 1. 观察官方注册输入

官方 EOS Utility 中，真实 R6 III 模型和描述符交给解析器后，输出 431,616 字节；随后交给 `EdsSetPropertyData(0x01000203, 33, ...)` 的数据与之逐字节一致，也与离线正常编译输出一致。

本次捕获的 setter 顺序是 `0x01000203 → 0x115`，目标槽此前已初始化，没有观察到额外的 `Set 0x114`。不能把其他工具可能采用的流程写成本次实测顺序。

### 2. 在正确 full33 输出中替换表

普通 Canon 参数编译可能从曲线、矩阵和色轴重建色表。本次诊断文件仅改变 dense 源表后，正常编译输出仍与基线相同；因此必须显式让 CUBE 变化进入最终表区。

新的路线保持真实模型、描述符、type10 和 372 字节原生头，将两张源表转换为 planar uint16LE RGB，范围 `0…32768`。量化关系为：

```text
native = (sample12 × 32768 + 2047) // 4095
```

每张最终表为 215,622 字节，分别替换偏移 372 和 215,994。该路线没有使用 R7 模型别名、17³ 虚表 hook 或 compact 色表 cipher。

实现见 [`native.py`](../src/r6lut/native.py) 和 [`convert.py`](../src/r6lut/convert.py)。

### 3. 补上独立工具的写入入口

格式突破先在官方注册流程中完成：严格匹配原输入后，仅替换一次 full33 数据，保留其余官方流程与真实返回值。

随后独立封装时，公开 `EdsSetPropertyData` 包装层对私有风格属性返回 9。代码仅在 `0x01000203` 且返回 9 时，使用固定 SDK 导出的 `CEdsObject::SetPropertyData` 同参数分发入口，随后正常写入 `0x115` 设置。它不是所有错误的通用重试，也不表示公开 API 在所有进程中永远不可用；官方捕获中的公开 setter 曾返回 0。

实现见 [`eds_r6_tool.m`](../src/eds_r6_tool.m)。

### 4. 用真正设备结果验收

新流程显式请求设备操作 `0x9189`，失败时不以缓存 getter 代替。431,616 字节输入与 83,076 字节读回分开验证，不要求不同格式逐字节相等。

历史验证包括：

- 恒等 LUT 的实时取景和机内 JPEG 颜色正常。
- 红蓝交换在实时取景和真实机内 JPEG 中出现预期颜色变化。
- 用户实际断 USB、关机重启、重新连接后，9 项属性保持一致，重启后 JPEG 仍呈现诊断效果。
- 后续独立工具完成过三个用户槽的创意 LUT 写入与新进程读取；没有为该批次每个 LUT 重做实拍或重启试验。

这建立了限定环境中的成像与持久性证据，不等于已获得任意 LUT 的逐色精度标定。也没有闭合一套通用、精确的 full33→packed17 数学转换。

## 与后续功能的区别

C-Log 照片适配解决输入颜色编码问题；USB 自动识别修正解决 IOKit 过滤与就绪时序；照片预览解决电脑端显示问题。它们都不能取代正确的相机载荷格式或机内验收。

本工具从 CUBE 生成的 dense PF3 需要配套 full33 注册；官方 PSE 参数型 PF3 属于正常官方注册路线。读回备份不是可直接发送的 full33 恢复载荷。
